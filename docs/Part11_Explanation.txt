=====================================================================
PART 11 - QoS: THREE PRIORITY QUEUES, WEIGHTED ROUND ROBIN, AGING
=====================================================================

1. WHAT PART 11 IMPLEMENTS
--------------------------
Until Part 10 every output queue had ONE class: a frame of any priority waited in arrival order. Now each port has three queues
(0 high, 1 normal, 2 low). The sender of a port takes its next frame with a scheduler: weighted round robin (5:3:1 by default,
from wrr_weights) and an aging override (prio_aging_ms) so that a low-priority frame is never starved.

Files:   include/queue.h, src/queue.c     the three rings, outq_set_sched(), sched_pick()
         src/forward.c, include/port.h, src/port.c   the bad_prio counter, its log line and the summary at teardown
         src/reload.c                      the weights and the aging time reach the scheduler at start-up and on SIGHUP
         tests/test_qos.c                  scheduler unit tests (normal, TSan, valgrind)
         tests/test_qos.py                 end-to-end tests with the real switch (normal, TSan, valgrind)
         tests/test_queue.c, tests/test_mactable.c, tests/test_config_signals.py   adapted (section 7)
         tests/run_unit.sh, tests/run_all.sh, README.md (the priorities and the two keys), docs/Part11_Explanation.txt, notes/bugs.md
Not touched: the wire protocol, the MAC table, the receiver and sender loops (the sender still calls outq_pop; the receiver still
calls outq_try_push through forward_frame), the lock order.


2. THE DESIGN (src/queue.c)
---------------------------
   outq_t: ring[0..2] (each with room for cap = queue_capacity frames), head/tail/count per class, credit[0..2], ONE mutex and ONE
   condition variable for all three. Memory: 3 x cap x 24 bytes per UP port.

   outq_try_push(q, f)      class = f->prio, a value above 2 counts as 2. Fullness is checked PER CLASS: a full low ring refuses low
                            frames only; high and normal are still accepted. Never blocks. The caller keeps its reference when it
                            returns false (unchanged Part 4 rule).
   outq_pop(q, &f)          sleeps while ALL rings are empty (while-loop on the predicate "total count == 0 and not closing"); then
                            sched_pick() chooses the class and the head of that ring is taken.
   sched_pick(q)            (q->lock held, total count > 0)
     1. Aging override: if the head of the LOW ring (then of the NORMAL ring) has waited more than prio_aging_ms
        (now - enq_time), pick it. This uses no credit, so the 5:3:1 rhythm of the other frames is undisturbed.
     2. Otherwise the first class c in the order 0, 1, 2 with count[c] > 0 and credit[c] > 0: credit[c]--, pick it.
     3. If no class qualifies, credit = weights and repeat step 2. It ends: some ring is not empty and every weight is >= 1.
   With 5:3:1 and every class busy a round is H H H H H N N N L. A class that is empty is skipped without losing its turn for
   the others; its unused credit is simply discarded at the next reset.

   The settings (weights, aging time) are held in queue.c as atomics and set with outq_set_sched(weights, aging_ms): there is one
   setting for every port, and queue.c does not need the switch's globals (the unit tests link it alone). The configuration code calls
   it in config_install() at start-up and in reload_config() on SIGHUP, with the weights and prio_aging_ms of the file. Values below 1
   are raised to 1 (a weight of 0 could make step 3 loop for ever). sched_pick reads them without any lock, so it never takes config_lock
   while holding the queue lock (config_lock is a leaf and is "taken alone"). A change applies at the next credit reset (weights) or the
   next pop (aging); the rest of a round uses the old credits. The three weights are three separate atomic loads: a reload in the
   middle of a reset can give one round a mixture of old and new weights; that is harmless.

   Lock order is unchanged: ports_lock -> queue lock -> ref_lock (outq_drain unrefs while holding the queue lock). sched_pick takes
   no other lock. The sender still writes with no lock held.


3. BAD PRIORITIES
-----------------
   A frame with prio > 2 is not valid. It is queued as low priority (frames are not rewritten: the same shared frame goes to every output
   port, and the receiving host sees the priority it was sent with). forward_frame counts it on the INGRESS port (port_t.bad_prio, an
   atomic counter reset when the port starts); the first one logs, after the ports_lock is released:
       port N: bad_prio: a frame with priority P (valid: 0-2) is queued as low priority; further ones are only counted
   and when the port closes the reaper logs the total:  port N: bad_prio: K frames with a priority above 2 were queued as low priority.
   So there is one bad_prio line per port while it is up, however many frames follow.


4. WHAT THE ROADMAP ASKED, AND WHERE IT IS
------------------------------------------
   "Activate ring[0..2], each with capacity queue_capacity"            outq_init (3 rings of cap); queue_capacity is per class
   "The receiver chooses the ring by prio; >2 is 2 and counted"        outq_class_of(), forward_frame, port_t.bad_prio
   "Fullness is checked per class; the drop is counted"                outq_try_push; forward_frame counts STAT_DROP of the port as before
   "outq_pop calls sched_pick"                                         yes (aging first, then credits, then reset)
   "The ratio is 5:3:1 with a frozen consumer"                         test_qos.c test_ratio
   "A low frame is sent within ~200 ms plus one write under continuous high traffic"   test_qos.c test_starvation (section 6)
   "The HOL test from Part 4 still passes"                             tests/test_forward.py: unchanged, passes

6. TESTS (methodology)
----------------------
   tests/test_qos.c (1293 checks; normal, TSan, valgrind with --track-fds):
     classes         0/1/2 and 3, 7, 255 -> low; pushes of mixed priorities land in the right rings; drain frees every ring
     settings        set/get; values below 1 are raised to 1
     per-class full  a full low ring refuses low and still accepts high and normal; when high fills, normal still accepts; a pop frees a slot of
                     that class only; a closing queue accepts nothing
     5:3:1 exactly   all three rings filled (64 each) BEFORE the consumer runs; the first 12 rounds are H H H H H N N N L (hard-coded), 15:9:3 in
                     the first 27 pops, the whole 192-pop sequence equals a reference model, every class is FIFO
     other mixes     1:1:1, 7:1:1, 2:2:2, 1000:1:1; only two classes busy (N N N L ...); one class busy; few H and many N
     random          20,000 random pushes/pops give the same order as the reference model (and a frame is refused only when ITS class is full)
     weights change  after H H with 5:3:1, set 1:1:1 (like a SIGHUP): the rest of the round uses the old credits (H H H N N N L), then H N L ...
     aging           an aged low frame jumps the weights (1000:1:1) and uses no credit; low before normal when both are aged; young frames are not
                     overtaken when the aging time is long
     starvation      the roadmap's criterion: a producer keeps the high ring non-empty, the consumer needs 3 ms per frame, weights 1000:1:1,
                     aging 200 ms: the low frame leaves after 202 ms (>= 150 ms, < 603 ms checked); CONTROL without aging: still waiting after 1.2 s
     concurrent      4 producers (one with bad priorities) and one consumer: every accepted frame comes out exactly once, FIFO per producer, no frame
                     leaked (frame_live_count)
     blocking pop    sleeps on an empty queue and wakes for a low frame
   Model comparison: the reference model is the algorithm of the roadmap written again independently in the test; the hard-coded 5:3:1 rounds
   do not depend on it.
   tests/test_qos.py (end to end, the real switch, queue_capacity = 8):
     the technique: C has a tiny receive buffer and never reads; D reads everything; A floods 17 MB of low-priority frames for them. That is far more
     than the socket buffers hold, so when the flood is over the sender thread of C's port is blocked in write() and all its rings are full
     (checked: thousands of drops are logged). Then A sends six marked frames n1 h1 n2 h2 n3 h3 (normal/high alternating). D, which reads, sees them (so
     the switch has queued them for C as well). Only then C starts reading: the ORDER in which the frames leave is the scheduler's.
     1 order             h1 h2 h3 n1 n2 n3 although n1 was sent first; exactly H H H N N N L at the start of the run; 5 or more queued low frames are
                         overtaken (arrive after n3); high and normal were never dropped while the low ring overflowed
     2 SIGHUP weights    1,1,1: the order becomes h1 n1 h2 n2 L h3 n3 L; back to 5,3,1: h1 h2 h3 n1 n2 n3 L; the log says the weights are "applied"
     3 bad priorities   3, 9 and 255 on one port and 200 on another: all five frames are forwarded; ONE bad_prio line per port; the summary
                         "3 frames ..." / "1 frame ..." when each port closes; a port with valid priorities has none
     4 wire unchanged   the receiving host sees prio=9 and the payload as sent
     5 normal traffic   15 frames of three priorities between two hosts arrive in order inside each class
     6 (valgrind)       order, bad_prio, reload, SIGINT: 0 errors, 0 bytes in use, nothing lost, no descriptor open
     tsan mode: tests 1, 3 and 5.
   Mutation check (the tests must be able to fail): a queue that ignores the priority (test_qos: 479 checks failed, no hang); a reload that does
   not hand the weights to the scheduler (test_qos.py failed); a bad_prio line for every bad frame (test_qos.py failed, after the assertion was
   made stricter, section 9). Sources restored (diff clean).
   Honest limit: the timing criterion (a low frame sent within ~200 ms + one write) is tested at the level of the queue (a controlled consumer).
   End to end it cannot be measured cleanly: the kernel buffers of the socket, not the scheduler, decide how long a frame waits before it is read.


7. CHANGES TO EXISTING TESTS (not weakened)
-------------------------------------------
   * tests/test_queue.c (Part 4): its frames come from frame_new(), whose priority is 0. Since the priority chooses the ring they would now go
     to the HIGH ring while the tests look at the NORMAL one. The fixture mk() now sets prio = 1 (normal); every assertion is as it was.
   * tests/test_mactable.c: queued(port) counted only the normal ring; it now sums the three rings (the tests ask "how many frames are queued
     for this port", not "in which class"). Same strictness.
   * tests/test_config_signals.py (Part 10): it asserted that wrr_weights and prio_aging_ms are "stored" (no effect yet). Since Part 11 they are
     applied, so it now asserts that the log says "applies ..." and no longer "stored". rate_limit, port.N.vlan and port.N.rate are still
     "stored" and still asserted as such.
   * tests/test_forward.py: found by the user's `make test` on a busy machine (notes/bugs.md item 22): it expected frames of three different priorities to
     arrive in the order they were sent (Part 11 reorders them by design when they are queued together), and had three checks that measured the speed of the
     machine (a fixed frame count, a 10 % floor, a comparison of counts between two runs made under different load). Now: frames are matched by content; the
     "B is still served after the dead host" check uses a high-priority marker; the head-of-line scenarios run at the same time and are compared by combined
     RATE; the floors are sanity floors. Under 4 busy loops on 2 cores the old version passed 1 of 4 runs, the new one 16 of 16; mutations (a queue that drops
     high-priority frames, a queue that blocks when full) still fail it.
   Everything else is unchanged; the head-of-line scenarios of the Part 4 test still test the same property (A's flood is not stalled, the fast hosts keep
   receiving).


8. LOCKS (unchanged)
--------------------
   ports_lock (1) -> queue lock (2) -> ... -> ref_lock (5) -> logger lock (6) -> stats (7). The scheduler settings are atomics (no lock);
   bad_prio is an atomic counter; the bad_prio log line is written after ports_lock is released.


9. BUGS AND MISTAKES FOUND
--------------------------
   No defect in the switch was found by the Part 11 tests. Mistakes in my own tests (notes/bugs.md item 21):
   * "queue full" in the log does NOT mean that the sender is blocked: with the default socket buffers (several MB) the switch swallowed the
     flood and the rings drained again when A stopped, so the marked frames went out in arrival order. Fixed by a tiny receive buffer on C and a
     flood of 17 MB, and by asserting that thousands of drops happened. (It had "passed" once by luck before.)
   * the unit test could HANG when a mutated queue did not hold the frames it expected (a blocking pop on an empty queue). Pops in the tests no longer block
     (they report -2), and test_qos has an alarm() backstop.
   * the bad_prio assertion only looked for "priority 3 ", so a switch that logged every bad frame still passed; found by the mutation check, now it
     counts every bad_prio line of the port.

11. LIMITATIONS AND DECISIONS FOR THE USER
------------------------------------------
   * The weights and the aging time are the same for every port (one setting in queue.c). The roadmap has no per-port setting.
   * Aging is evaluated when the sender picks the next frame, so a frame can wait "prio_aging_ms plus one write" (what the roadmap says), not less.
     A sender that is blocked in write() cannot pick anything until the write ends.
   * queue_capacity is per class, so memory per UP port is 3 x queue_capacity x 24 bytes: with the largest value of the configuration (65536) that is
     4.7 MB per port and 300 MB for 64 ports.
   * The drop counter is still one per port. Which class dropped is not recorded (Part 14 may add it).
   * Frames with a priority above 2 are queued as low and counted, not dropped or rewritten (the roadmap says "treated as 2").
   * The end-to-end tests depend on a flood that is far beyond the socket buffers (17 MB per scenario).
