PART 21 - BONUS: BENCHMARK (GLOBAL LOCK VS STRIPED LOCKS VS RWLOCK)
=====================================================================

1. WHAT THE ROADMAP ASKS
------------------------
A compile-time switch in mactable.c: -DMAC_LOCK=STRIPED (default) | GLOBAL (one mutex) | RWLOCK (one pthread_rwlock_t; lookups take the read lock, learn and age the write lock). make bench builds
switch_global, switch_striped, switch_rwlock. bench.c: ./bench <ip> <port> <hosts> <seconds> <payload>: H connections, each with a sender thread (unicast to random peers after a warm-up broadcast so
that MACs are learned) and a reader thread counting frames; prints the total frames/s received. bench_mac: an in-process micro-benchmark linking mactable.c directly, T threads, 90/10 lookup/learn
for a fixed time. bench/run.sh -> CSV for H or T = 1, 2, 4, 8, 16 -> plot.py or gnuplot -> bench/throughput.png and a 1-page bench/report.pdf. All builds -O0. Every point run 3 times, the median
reported; fixed seeds; the report states the machine, the cores and the explanation. Completion: all three variants pass forward.sh; the graph and the report exist and the numbers can be reproduced.

3. DESIGN DECISIONS
-------------------
* One source file, three builds: the callers of the lock are the same code, so the comparison is fair. The rule that makes it safe is the old one: at most ONE of these locks is held at a time.
* The roadmap's "H or T = 1, 2, 4, 8, 16": the in-process benchmark uses T = 1, 2, 4, 8, 16; the network benchmark uses H = 2, 4, 8, 16, because with ONE host nothing can be delivered (there is no
  peer) and the point would be a flat zero.
* bench warms up by REPEATING each host's broadcast until every host has heard every other (the switch accepts connections one at a time, so an early broadcast can miss a host); broadcasts are never
  counted; the counted frames are unicast. bench_mac checks every lookup answer and mac_check_counts() at the end, so a variant that is fast but wrong cannot pass.
* matplotlib and gnuplot are not installed here (and installing software was not asked for): plot.py draws the graph and the report with PIL, which is. It is a function of the CSV files only (the test
  checks that two runs give byte-identical results.csv and PNG; the PDF page renders identically, the file differs only by the creation date PIL embeds); the text of the report is generated from the numbers.
* Machine: 2 logical CPUs (i7-6600U). Points above 2 threads / hosts are oversubscribed; the report says so.

4. RESULT (bench/report.pdf, bench/results.csv; 5 s per point, median of 3)
----------------------------------------------------------------------------
MAC table alone (operations/s):  threads 1 / 2 / 4 / 8 / 16
   global   7.20M / 3.36M / 3.29M / 3.48M / 5.35M
   striped  6.50M / 9.80M / 10.09M / 9.80M / 10.15M
   rwlock   7.35M / 0.85M / 2.46M / 2.98M / 2.80M
Whole switch (frames received/s):  hosts 2 / 4 / 8 / 16
   global   49.4k / 43.7k / 37.4k / 33.3k      striped  50.9k / 43.9k / 41.6k / 28.1k      rwlock  46.9k / 42.8k / 39.5k / 26.4k
* Striped locking scales to the cores (1.5 x its 1-thread value on 2 cores); the global mutex loses about half at 2 threads; the single rwlock is the WORST (an eighth at 2 threads), contrary to the usual
  expectation: all readers update the same lock word and the 10 % learns block everybody. The global lock recovers partly at 16 threads (oversubscribed machine; stated in the report).
* In the whole switch the three variants are the same within the noise (the runs of one variant differ by up to 42 %): one delivered frame costs about 20 us of the machine, one table operation about
  140 ns, so the lock is not the bottleneck of the switch; the micro-benchmark is what shows it.
The numbers depend on the machine and on what else runs on it; the seeds, the method and the raw CSV files are in the repository.
